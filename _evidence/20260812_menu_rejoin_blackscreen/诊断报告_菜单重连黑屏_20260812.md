# 诊断报告：菜单重连后「光标/事件影响未同步 + 进入下一节点黑屏」

- **日期**：2026-08-12
- **模组**：AutoReconnectMinCore（独立 mod，版本 **v0.9.32-core**，双端日志均确认 `ModuleInitializer 触发 v0.9.32-core`）
- **场景**：非战斗客机主动退出 → 主机暂停菜单邀请重连 → 重连成功 → 客机观察到光标/事件影响未同步 → 进入下一节点时黑屏
- **结论（2026-08-12 19:08 修正）**：重连流程本身成功；黑屏是「整局重建」保真度不足导致客机与主机状态分歧，在**节点 (5,5) 切换的「双方就位」同步屏障**处双方一起卡死（挂起）所致——**主机并未主动退出**，其 `NGame.Quit` 是黑屏后 Alt+F4 关游戏。根因在 **MenuRejoin 整局重建无法完美还原主机实时瞬态**。

## 4. 根因分析

### 4.1 直接根因：MenuRejoin「整局重建」保真度不足
重连走的是 `MenuRejoinFlow.EnterRunFromRejoin`：
```
RunState.FromSerializable(run)            // 反序列化主机回传的 serializableRun
→ RunManager.SetUpSavedMultiplayer(...)  // 重建多人局
→ game.LoadRun(runState, run.PreFinishedRoom)  // 加载到当前房间
```
`QuestionRoomResolvePatch` 只补上了 "?" 房间**重摇**这一个已知缺口（避免 Unknown 节点摇出与主机不同的房间类型）。但重建路径仍有**固有信息损失**：

1. **地图光标位置（"光标未同步"）**：重建后的 `VisitedMapCoords` / 当前坐标能还原到 (6,4)，但"光标当前高亮/选中哪一格下一步"这种 UI 瞬态依赖原生进入流程，重建不一定完全一致。
2. **事件已结算效果（"事件影响未同步"）**：`WOOD_CARVINGS` 这类事件，`serializableRun` 带回的是房间状态，但事件**选项效果的本地结算**（如 TORUS 把 STRIKE_REGENT 变化为 ToricCard 后牌组是否即时刷新）在重建重进时可能未触发/未刷新 → 客机牌组与主机不一致。
3. **当前房间之后的 RNG 偏移**：`serializableRun` 带的是重建**那一刻**的 RNG 状态。若主机在客机断开期间已推进过任何消耗 RNG 的动作（本例主机在 18:38:15 已进入 WOOD_CARVINGS，客机 18:38:21 才退），重建快照与主机实时态之间就存在 RNG 步差 → 进入下一节点 (5,5) 后首个消耗 RNG 的环节（敌人意图、抽牌、事件摇奖）即分歧。

→ 进入 (5,5) 时分歧已积累到让客机**过不了节点切换的「双方就位」同步屏障**：主机 `MoveToMapCoordAction (5,5)` 需等客机到达新节点确认，而分歧的重建客机永远到不了就位态 → 主机该动作卡住不完成、双端渲染冻结（黑屏）。

### 4.2 修正：主机黑屏 = 节点切换同步屏障「挂起」，而非主动退出
- 主机 godot.log L5544 `MoveToMapCoordAction (5,5) began executing` 之后**没有任何 `finished execution`**（直到 11 秒后 Alt+F4）。即主机切到 (5,5) 的动作**启动后卡死未结束**。
- STS2 的节点切换是「双方就位」同步屏障：主机 `MoveToMapCoordAction` 需等客机到达新节点并确认。重建出的客机因状态分歧（RNG/事件/光标缺口）**永远到不了 (5,5) 的就位态**，于是主机这一动作无限等待 → 主机渲染冻结（黑屏）。客机侧同样卡在节点加载 → 双端同时黑。
- 因此**主机并未主动退出**：其 `NGame.Quit()`（L5548）是用户看到双端已黑、用 Alt+F4 关游戏的收尾。文件最末只有正常退出时的 RID 泄漏提示（L5563-5585），**没有任何异常栈 / `ReturnToMainMenuWithError`**——证实主机不是崩溃，而是被同步屏障挂起后由用户强关。
- 客机日志里那两条 `not connected` 报错是主机断开（reason 1001）之后的清场副作用，不是根因。

### 4.3 与历史问题的同质性
这与 v0.9.27-core 发现的"整局重建 RNG 分歧"是**同一类问题**：只要走"销毁客机 run + 从主机存档重建"，就无法 100% 保真。v0.9.28 用"战斗态比对 + 仅在分歧时整局重建"缓解了战斗内场景，但**菜单重连（客机已无内存 run）只能硬重建**，所以该类分歧在菜单重连路径上必然残留。

### 4.4 为什么「15 秒内的重连」没有保真度问题？
关键在「重连那一刻，客机内存里是否还有活的 run 与 NetService」：

- **15 秒内快速重连（Card3「不回退」路径）**：客机只是传输层掉线（`NetClient.Disconnect`）。此时 `RunManager.Instance` 与 `NetClientGameService` 旧实例**仍驻留内存**，`_messageBus` 里全部战斗同步 handler（PeerInputMessage / SyncRngMessage / ChecksumDataMessage / StateDivergence）一个未清，客机的 `run`（地图、事件已结算效果、RNG 状态、光标位置）原样保留。重连只做一件事：重拨 `NetClient` 传输层 + 重跑握手，然后继续用**已有的 run 与 handler** 跑。没有「销毁→重建」，所以：地图光标 ✓ 在内存、事件效果 ✓ 已生效、RNG ✓ 未重置、handler ✓ 原样 → 100% 保真、零分歧。这正是已验证的战斗内重连（零感接回、前 165 条 Checksum 一致）。
- **菜单重连（客机已回主菜单 / run 被销毁）**：退出时 run 已被 `RunManager` 清理，内存无 run。重连只能走 `MenuRejoinFlow.EnterRunFromRejoin` 从主机回传的 `serializableRun` **反序列化重建整局**。凡未被序列化进 `serializableRun` 的运行时瞬态（地图光标 UI 态、事件选项本地即时结算刷新、当前房间之后的 RNG 偏移）都会丢 → 进入 (5,5) 时分歧爆发，客机过不了节点同步屏障，双端卡死黑屏。
- **「15 秒」的本质**：是游戏内置「断线宽限期」。宽限期内客机 run + NetService 未被销毁，Card3 复用路径能找到活实例 → 不重建 → 无保真问题；超过宽限，游戏把 run 判为放弃、回主菜单并销毁，重连只剩重建一路 → 回到本 bug 的保真缺口。所以「15 秒内无保真问题」=「run 还活着时不重建」；一旦 run 死了必须重建，就踩中本 bug。

## 5. 修复方向（待你拍板，本次未改代码）

### A. 扩展 Card3「不回退」到主动退出场景（推荐，根治）
- 思路：客机**主动退出时不销毁 run**（抑制 `RunManager` 清理，仅做优雅断连），run 常驻内存；主机重新邀请时，走 `ReconnectRunner` 的「复用旧 NetService / 只重拨传输层」轻量路径，而非 MenuRejoin 重建。
- 优点：从根上消除"整局重建类"分歧（与战斗内 Card3 同一套机制，已验证）。
- 代价：要处理 run 常驻主菜单的生命周期（超时清理、开新局/退游戏时清理、主机永不重邀时的幽灵 run）。

### B. 继续修补 MenuRejoin 重建保真度
- 思路：在 `EnterRunFromRejoin` / `QuestionRoomResolvePatch` 里补全地图光标、事件已结算状态、房间还原等瞬态。
- 优点：改动小、风险低、不影响其它路径。
- 代价：`serializableRun` 的瞬态缺失是结构性的，可能无法 100% 保真，理论上仍有残留分歧风险。

### C. 维持现状 / 仅报告
- 本次选择。先把诊断固化，确认方向再动。
